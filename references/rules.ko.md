# 작성 규칙 (한국어판)

모든 일지에 적용돼. 이 규칙과 사용자의 `DEVLOG.md`가 다르면 `DEVLOG.md`를 따라.

## 1. "결과"에는 프로젝트 작업만

**결과** 칸에는 `DEVLOG.md`에 적힌 프로젝트에서 실제로 바뀐 것만 써.
작성·수정한 코드, 만든 파일, 돌린 실험, 만든 문서, 적용한 결정.

- 공부한 것, 읽은 것, 설명 들은 것은 결과가 아니라 **배운 것**에 써.
- 가리킬 수 있는 결과물로 써: "업로드 API에 재시도 추가 (`api/upload.py`)" ○ / "업로드 API 작업함" ✕
- 프로젝트에 바뀐 게 없으면 `이번 세션에는 프로젝트 변경 없음.` 한 줄.

## 2. 배운 것: 정의 → 언제 → 역할

배운 개념 하나마다 짧게 세 줄, 항상 이 순서로:

```
#### <개념>
- 정의: 쉬운 말로 뭔지 (약어는 처음 나올 때 풀네임과 뜻까지)
- 언제: 어떤 상황에서 등장하거나 쓰이는지
- 여기서의 역할: 이 프로젝트에서 무슨 일을 했는지 (또는 할 건지)
```

대화에서 셋 중 하나를 다루지 않았으면 지어내지 말고 `(다루지 않음)`이라고 써.

## 3. 출처 등급

배운 것·결정에 들어간 사실 중 바깥 출처에서 온 것에는 등급을 붙여. `[A1]`, `[C2]`처럼 출처 옆에.

글자 — 출처를 얼마나 믿을 수 있나:

| 등급 | 출처 |
|---|---|
| A | 공식 문서, 표준·명세, 논문, 프로젝트 자체 코드·데이터 |
| B | 잘 알려진 2차 자료 (검증된 교재, 기업 기술 블로그) |
| C | 커뮤니티 답변, 개인 블로그, 포럼 글 |
| D | 확인 안 됨: 에이전트의 배경지식, 전해 들은 말, 출처 없음 |

숫자 — 이번 세션에서 어디까지 확인했나:

| 등급 | 뜻 |
|---|---|
| 1 | 여기서 직접 확인: 코드 실행, 출력 확인, 문서를 열어 읽음 |
| 2 | 다른 독립 출처 하나 이상과 일치, 여기서 실행은 안 함 |
| 3 | 확인 안 됨 |

D나 3 등급에 기대는 결정이 있으면 **남은 질문**에도 같이 적어.

## 4. 대화에 없던 사실은 쓰지 않기

대화에 실제로 있는 것만 써. 일반 상식으로 빈칸 채우기, 파일 이름·숫자·날짜·이유 추측 금지.
결정 이유가 대화에 안 나왔으면 `이유: 언급 없음`이라고 써. 그 빈칸도 쓸모 있는 정보야.

## 5. "기록 금지" 지키기

`DEVLOG.md`의 "기록 금지" 목록에 해당하는 건 빼 (예: 비밀키, API 키, 개인정보, 내부 주소, 팀원 실명).
애매하면 빼고, 답할 때 뭔가 뺐다는 사실만 말해. 뺀 내용을 다시 말하지는 마.

설정과 상관없이 항상 빼는 것: 비밀번호, 토큰, 키, 접속 문자열(connection string).

## 6. 꼬꼬무 맵 (map.json)

호기심이 어떻게 결정이 됐는지를 따라가는 지도야:

```
root (프로젝트)
└─ task      하려던 일
   └─ question  하다가 생긴 꼬리 질문 ("왜…?", "만약…?")
      └─ insight   알아낸 것
         └─ decision  그래서 정한 것
```

- 질문이 또 다른 질문으로 이어질 수 있어 (그게 꼬꼬무). 연결을 끊지 마.
- 모든 줄기가 결정까지 갈 필요는 없어. 열어 두면 대시보드에 "남은 질문"으로 잡혀.
- 모든 노드에 `date`, insight·decision 노드에는 등급 붙은 `source`를 달 수 있어.
- `type` 값은 영어(`task`, `question`, `insight`, `decision`) 그대로 둬. 대시보드가 이 값으로 색을 칠해.
